# Agent Worklog v0.4.0 Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish Agent Worklog v0.4.0 with outcome-oriented bilingual capability summaries, consistent version metadata, verified artifacts, and a successful PyPI installation smoke test.

**Architecture:** Keep the current application behavior feature-frozen. Make four independently reviewable documentation and metadata changes, protect them with focused pytest tests, then pass the existing release gate before merging through GitHub and tagging the exact successful `main` commit.

**Tech Stack:** Python 3.11+, pytest, uv, Ruff, Pyright, Hatchling, Twine, GitHub Actions, GitHub CLI, PyPI Trusted Publishing.

## Global Constraints

- v0.4.0 is feature-frozen at the current `main` behavior.
- Do not add new harness behavior, report formats, CLI options, dependencies, or output integrations.
- `README.md` and `README.zh-TW.md` must present the same ten product outcomes in the same order.
- The capability sections may name OpenCode and Claude Code as supported harnesses, but must not explain `opencode export`, `~/.claude/projects`, or `opencode stats`.
- The source constant, project metadata, lockfile, built distribution, and published package must all report version `0.4.0`.
- Do not create or push `v0.4.0` until the release pull request and its `main` merge commit have both passed CI.
- PyPI releases are immutable; never move or replace a published tag or version.
