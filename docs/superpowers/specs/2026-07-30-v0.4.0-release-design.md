# Agent Worklog v0.4.0 Release Design

## Goal

Publish the Claude Code adapter and its supporting fixes as Agent Worklog
v0.4.0, while making the English and Traditional Chinese capability summaries
describe product outcomes instead of alternating between harness-specific
implementation details.

## Context

The Claude Code adapter is merged into `main` and recorded under
`CHANGELOG.md`'s `Unreleased` section. The repository has no open issues or
pull requests, the latest `main` CI run passed, and the local release checks
currently pass with 153 tests and 88.98% coverage. The latest published version
is v0.3.0.

The current `Capabilities` / `功能` lists mix user-visible outcomes with details
such as `opencode export --sanitize`, `~/.claude/projects`, and the two token
usage sources. That makes the reader repeatedly switch between OpenCode and
Claude Code behavior before learning what Agent Worklog does.

## Scope

v0.4.0 is feature-frozen at the current `main` behavior. The release contains:

- the already-merged Claude Code adapter and fixes listed under `Unreleased`;
- outcome-oriented capability lists in `README.md` and `README.zh-TW.md`;
- a correction to the stale stderr limitation in
  `docs/claude-code-adapter-design.md`;
- the v0.4.0 changelog section, package version constants, version-consistency
  test, and lockfile update; and
- release verification, tagging, publication, and post-publication smoke
  testing.

No new harness behavior, report format, CLI option, dependency, or output
integration is added.

## Capability-List Design

Both READMEs will briefly identify OpenCode and Claude Code as supported
harnesses, then describe only behavior shared at the product level. The English
section will use this meaning:

- discover coding-agent sessions across projects independently of the current
  working directory;
- select sessions by recent days, calendar week, or explicit date range;
- group Git worktrees belonging to one repository;
- preserve repository attribution for child and subagent sessions, with
  `--root-only` available to exclude them;
- report session titles and working directories by repository;
- summarize model and token usage when the selected harness provides it;
- retain source activity IDs and confidence levels as supporting evidence;
- check session information for common secret patterns before reporting or
  optional LLM transmission;
- continue past an unreadable individual session and report a warning; and
- write owner-only `0600` report files on POSIX systems.

`README.zh-TW.md` will express the same ten outcomes naturally in Traditional
Chinese. It does not need to mirror English word-for-word, but it must preserve
the same scope and order.

The capability sections will not explain:

- `opencode export --sanitize`;
- the Claude Code transcript directory;
- the OpenCode or Claude Code token source;
- whether a harness requires an installed CLI; or
- harness-specific usage-window and verification limitations.

Those details remain in the existing Requirements / 系統需求, Getting Started /
快速開始, Usage / 使用量統計, Privacy / 隱私, and limitations sections.

## Documentation Review Gate

Human-facing prose will be reviewed directly instead of adding source-text
tests that would only detect intentional copy edits. Before the release gate,
reviewers will compare the English `Capabilities` section and the Traditional
Chinese `功能` section side by side and confirm that both name the two supported
harnesses, contain the same ten outcomes in the same order, and do not explain:

- `opencode export`;
- `~/.claude/projects`; and
- `opencode stats`.

The Claude Code design limitation and v0.4.0 changelog will likewise be
validated through focused diff review. The version-consistency requirement
remains protected by an executable unit test because it is a runtime/package
metadata contract rather than human prose.

## Claude Code Design-Document Correction

The first known limitation in `docs/claude-code-adapter-design.md` is stale: it
still says non-empty stderr can be classified as an error, but the merged
implementation deliberately stopped treating stderr alone as success or
failure. The limitation will instead state that Claude Code transcripts expose
no observed command exit code, so reports cannot claim that verification passed
or failed. This will agree with the README, changelog, tests, and current
extraction behavior.

## Release Metadata

The current `Unreleased` entries will move under `## 0.4.0`, and a fresh empty
`## Unreleased` heading will remain at the top. The v0.4.0 section will also
mention the generalized capability summaries and corrected Claude Code
limitation.

`pyproject.toml` will change the project version from `0.3.0` to `0.4.0`.
`src/agent_worklog/__init__.py` will change its stale `__version__` value from
`0.1.0` to `0.4.0`. A focused unit test will read `[project].version` from
`pyproject.toml` and assert that it equals `agent_worklog.__version__`, preventing
the two version declarations from drifting again. `uv lock` will regenerate
`uv.lock` so the root package version matches.

## Verification

Before the release pull request is opened, run the documented release gate:

```bash
uv sync --locked --extra dev
uv run pytest --cov=agent_worklog --cov-fail-under=80
uv run ruff check .
uv run pyright
uv build
uv tool run twine check dist/*
```

The documentation tests must demonstrate that the capability lists stay
general. CI must pass on the release pull request and on the merge commit before
tagging.

## Delivery

Release work will use the `codex/release/0.4.0` branch. Changes will be reviewed
through a pull request into `main`. After that pull request is merged and the
merge commit's CI succeeds:

1. update the local `main` reference to the exact successful merge commit;
2. create annotated tag `v0.4.0` on that commit;
3. push only the tag;
4. monitor the Release workflow through completion;
5. confirm the GitHub Release contains the wheel and source distribution;
6. confirm PyPI exposes `agent-worklog==0.4.0`; and
7. install v0.4.0 into a clean temporary environment, assert that
   `importlib.metadata.version("agent-worklog")`,
   `agent_worklog.__version__`, and `"0.4.0"` are equal, then run
   `agent-worklog --help`.

## Failure Handling

- A local verification, pull-request CI, or merge-commit CI failure blocks tag
  creation.
- A release workflow failure is diagnosed before any retry. The tag is not
  moved or silently replaced.
- PyPI files and versions are immutable. If v0.4.0 reaches PyPI and a defect is
  then found, the correction is published as a subsequent patch release rather
  than overwriting v0.4.0.
- Post-publication verification reports the exact GitHub Release, PyPI version,
  and smoke-test result so partial publication is visible.

## Success Criteria

- The two README capability sections are outcome-oriented and semantically
  aligned.
- Harness-specific acquisition and accounting details remain documented in
  their dedicated sections.
- The stale Claude Code stderr limitation is corrected.
- The source constant, project metadata, lockfile, built distribution, and
  published package all report version 0.4.0.
- All local and GitHub release gates pass.
- GitHub Release and PyPI both publish v0.4.0 artifacts.
- A clean environment can install the published package and invoke its CLI.
